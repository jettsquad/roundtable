# 需求—设计—计划 追溯（spec-trace）

## 这个 skill 管什么，不管什么

**管：** 需求书、设计书、计划书这三份文档**彼此是否对得上**。

**不管：** 代码写得对不对、交付结果是否满足需求。那是执行阶段和验收阶段的事，各有各的检验（验收见 `spec-accept`）。

每个阶段只对自己的产出负责。如果后来验收发现「证据全过了，需求却没满足」，那是**这一阶段**的缺陷——证据没量到需求——应当回到这里改追溯表、改这个 skill，而不是在后面的阶段找补。

## 它防的是什么

一份计划可以每个批次都「出口全绿」，而需求没有满足。真实发生过：

- 计划写了「为 14 条验收各写一个界面测试」，出口脚本却只跑单元测试——**任务要求和出口判据是两处手写的，脱了节**。
- 界面类的需求，证据只有逻辑层测试——**证据的层级够不着需求**。
- 「遗留项写进交接文件即算交付」原本只列了三项，执行时被推广到一切做不完的东西——**缩小范围不需要任何人同意**。
- 批次出口检查是「提交记录里出现批次号」——**检查量的不是需求**。

结果：九个阶段全部通过，18 条需求里 5 条未覆盖，界面没接，新用户注册不了。

根因只有一个：**三份文档之间没有一张机器能查的对照表。** 本 skill 的全部内容就是建这张表，并让它查得出上面每一种漏洞。

## 需求由谁定

需求由**需求所有者**（人）决定。你可以起草、追问、指出矛盾，但不能替他删减或推迟任何一条。

## 核心产物：`trace.json`

放在计划目录里，和三份文档同处。格式见 `templates/trace.json`。四张表：

| 表 | 每一行是什么 | 必须回答 |
|---|---|---|
| `requirements` | 一条需求 | 落在哪些端、设计在哪、谁来做、**怎么证明做到了** |
| `tasks` | 计划里的一个任务 | 它为哪条需求而存在、归哪个批次 |
| `batches` | 一个批次（议程的一个节点） | 它名下有哪些证据 |
| `leftovers` | 一条没做完的事 | 它欠的是**哪条需求** |

### 证据（evidence）

一条证据是一条可以再跑一遍的命令，退出码 0 表示这条需求的这一面成立。「已人工确认」「见截图」「代码里有」都不是证据。每条证据要写四样：

| 字段 | 含义 |
|---|---|
| `run` | 命令 |
| `surface` | 它量的是哪一端（必须是该需求 `surfaces` 里的一个） |
| `level` | 它量到哪一层：`logic`（逻辑/单元）、`interface`（真的经过接口和存储）、`ui`（真的操作界面） |
| `failsWhen` | 什么情况下它会失败。写不出来，多半是它没量到东西 |

### 端与层级（surfaces）

每条需求写明它**落在哪些端**，以及每个端**至少要量到哪一层**：

```json
"surfaces": [
  { "name": "backend", "level": "interface" },
  { "name": "web", "level": "ui" },
  { "name": "ipad", "level": "ui" }
]
```

规则：**每个端至少有一条层级够的证据。** 一条「老师在 iPad 上给作业打分」的需求，如果 iPad 这一端只有逻辑层测试，脚本会报错——逻辑层测试证明不了界面接上了。

怎么定层级：需求说的是人看得见、点得到的东西，就是 `ui`；说的是系统对外的行为（接口返回什么、数据怎么存），就是 `interface`；只有纯计算规则才是 `logic`。拿不准时取高的。

### 批次出口不手写

`batches` 里**没有**出口检查字段。一个批次的出口就是：**它名下的全部证据都通过。** 由 `spec-accept` 的脚本直接运行这些证据来判定：

```bash
python3 ~/.agents/skills/spec-accept/scripts/run_evidence.py <计划目录>/trace.json --batch <批次号> --cwd <项目根目录>
```

校验通过后脚本会把每个批次的这条命令打印出来，原样用作议程里该阶段的出口检查。

为什么不许手写：出口脚本和证据一旦是两处，就会各走各的——计划要界面测试，脚本只跑单元测试。让出口**就是**证据，这个缺口不存在，执行的人也没有一个可以改松的出口脚本。

## 流程：验收先行

顺序不能换。先有证据，再有设计，最后才有任务。

### 第 1 步　把需求拆成可检验的条目

- 每条一个稳定编号（`R1`、`R2`…），之后只追加、不重排。
- 每条必须能回答：**怎样的一次操作、看到什么结果，算它成立？** 答不出的不是需求，是愿望——列出来退回给需求所有者，不要自己补全。
- 一条里有「并且」的，拆成两条。
- 逐段对照需求书：每一句带「必须、应、不得、可以」的话，都要落到某个编号上。**这一步脚本帮不了你**，它只能查编号是否出现在需求书里，查不出你漏拆了哪句。拆完请需求所有者过目。

### 第 2 步　定每条需求的端和层级，写证据——在写任何设计之前

- 先填 `surfaces`，再为每个端写证据。
- 此刻证据应该是**失败**的（功能还不存在）。现在就通过的证据，要么功能已有，要么没量到东西。
- 禁止不可能失败的命令（`true`、`echo ok`）。脚本会拒绝。

### 第 3 步　写设计，每一节挂到需求上

- 设计书每个决定标明它服务于哪些需求编号，登记进该需求的 `design`。
- 反查两遍：有没有需求在设计里找不到落点？有没有哪节设计不服务于任何需求（那是范围蔓延，删掉，或者回去请需求所有者加需求）？

### 第 4 步　写计划，任务从需求推出来

- 每个任务标明它为哪些需求而存在；每条需求至少有一个任务。
- **任务的「完成」= 它名下需求的证据通过。** 不用勾选框当完成标准。
- 把每条证据归入一个批次（`batches[].evidence`）。一条证据归在哪个批次，那个批次做完时它就必须通过。

### 第 5 步　跑校验，不过不交

```bash
python3 ~/.agents/skills/spec-trace/scripts/trace_check.py <计划目录>/trace.json
```

有任何一条报错就不算写完。

### 第 6 步　变更时

- 需求变了：先改 `requirements`，再顺着改证据、设计、任务，最后重跑校验。**不要只改计划。**
- 做不完的事：记进 `leftovers`，**必须**写明欠的是哪条需求。它算不算「不阻塞」不由记下它的人决定。
- 推迟一条需求：`status` 改为 `deferred`，并填 `deferral`（谁批准、哪天、为什么）。批准人必须是需求所有者。

## 校验规则

`trace_check.py` 在下列任一情况报错：

| 规则 | 它拦的是什么 |
|---|---|
| 生效的需求没有任务 | 需求写了没人做 |
| 生效的需求没有设计出处 | 设计漏了它 |
| 生效的需求没有写落在哪些端 | 不知道该量哪里 |
| 某个端没有层级够的证据 | 界面需求只有逻辑测试 |
| 证据量的端不在该需求的端里 | 证据量错了地方 |
| 证据没有命令，或命令不可能失败 | 假证据 |
| 证据没写「什么情况下会失败」 | 证据没想清楚量什么 |
| 证据没有归入任何批次 | 没有哪个出口会去跑它 |
| 任务不指向任何需求 | 范围蔓延 |
| 需求与任务互相引用不一致 | 两张表各说各话 |
| 批次名下没有证据 | 空批次 |
| 批次带了手写的出口检查 | 出口和证据脱节的入口 |
| 遗留项没有挂到需求上 | 自己决定「不阻塞」 |
| 推迟的需求没有批准记录 | 自己推迟需求 |
| 编号在对应文档里找不到（给了文档路径时） | 表和文档漂移 |

## 不要做的事

- 不要先写计划再回头补追溯表。那样表只会如实记录计划的漏洞。
- 不要让一条证据同时证明五条需求。一条挂了，分不清是哪条没满足。
- 不要把「跑全量测试通过」当作任何一条具体需求的证据。它证明的是没弄坏别的，不是做成了这件。
- 不要为了让校验通过而把层级写低。层级是需求决定的，不是测试写起来方便不方便决定的。
