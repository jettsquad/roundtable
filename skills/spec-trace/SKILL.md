# 需求—设计—计划 追溯（spec-trace）

## 这个 skill 管什么，不管什么

**管：** 需求书、设计书、计划书这三份文档**彼此是否对得上**。

**不管：** 代码写得对不对、交付结果是否满足需求。那是执行阶段和验收阶段的事，各有各的检验（验收见 `spec-accept`）。

每个阶段只对自己的产出负责。如果后来验收发现「证据全过了，需求却没满足」，那是**这一阶段**的缺陷——证据没量到需求——应当回到这里改追溯表、改这个 skill，而不是在后面的阶段找补。

## 它防的是什么

一份计划可以每个批次都「出口全绿」，而需求没有满足。真实发生过：

- 计划写了「为 14 条验收各写一个界面测试」，出口脚本却只跑单元测试——**任务要求和出口判据是两处手写的，脱了节**。
- 界面类的需求，证据只有逻辑层测试——**证据的层级够不着需求**。
- 「遗留项写进交接文件即算交付」原本只列了三项，执行时被推广到一切做不完的东西——**缩小范围不需要任何人同意**。
- 批次出口检查是「提交记录里出现批次号」——**检查量的不是需求**。

结果：九个阶段全部通过，18 条需求里 5 条未覆盖，界面没接，新用户注册不了。

根因只有一个：**三份文档之间没有一张机器能查的对照表。** 本 skill 的全部内容就是建这张表，并让它查得出上面每一种漏洞。

## 需求由谁定

需求由**需求所有者**（人）决定。你可以起草、追问、指出矛盾，但不能替他删减或推迟任何一条。

## 核心产物：`trace.json`

放在计划目录里，和三份文档同处。格式见 `templates/trace.json`。四张表：

| 表 | 每一行是什么 | 必须回答 |
|---|---|---|
| `requirements` | 一条需求 | 它对应需求书里的**哪几句话**、落在哪些端、设计在哪、谁来做、**每句话怎么证明做到了** |
| `tasks` | 计划里的一个任务 | 它为哪条需求而存在、归哪个批次 |
| `batches` | 一个批次（议程的一个节点） | 它名下有哪些证据 |
| `leftovers` | 一条没做完的事 | 它欠的是**哪条需求** |
| `guards` | 一条不属于任何需求、但出口都要过的检查 | 它防的是什么 |

表头还有四样，都是为了让「漏了」和「从没写过」能被区分开：

| 字段 | 含义 |
|---|---|
| `documents.requirements` / `design` / `plan` | 三份文档在哪。每一项可以是一个文件、几个文件的列表，或一个目录 |
| `documents.requirementIdPattern` | 需求书里需求编号的写法（正则），如 `"FR-\\d+|D\\d+"`。脚本用它把需求书里的编号全部找出来 |
| `documents.clauseHeadings` | 需求书里标题不带需求编号、但下面的条目同样要逐条交代的小节，如 `["验收"]` |
| `notRequirements` | 需求书里不是需求的编号或句子。每条写 `id` 或 `quote`、`kind`、`reason`。`kind` 只能是 `decision`（决策或背景）、`out-of-scope`（不在本期范围）、`separate-spec`（另起规格） |
| `acceptanceItems` | 需求书里验收条目的清单，如 `["1", "2", …, "15a"]`。需求所有者按这些逐条验收。需求书没有验收清单时写空列表 `[]`，不能不写 |

### 条款（clauses）：追到句子，不只追到编号

每一行用 `clauses` **原文引用**它负责的需求书里的句子：

```json
"clauses": [
  { "id": "FR-3.a", "quote": "0.5x–2x 倍速" },
  { "id": "FR-3.b", "quote": "左右方向键微调 0.5 秒" },
  { "id": "FR-3.c", "quote": "带动态水印" }
]
```

- 引文必须是需求书里的**原话**（脚本去掉空白后逐字比对），不是转述。
- 一句话里用顿号、逗号并列了几件事，就拆成几条条款，各引各的那一段。
- 一行可以引用需求书里不同地方的句子：一条验收条目和它对应的功能小节里的那几句，是同一件事，放在同一行。

脚本会反过来查：需求书里每个带需求编号的小节（以及 `clauseHeadings` 声明的小节）下面的**每一个列表项和表格行**，都必须被某一行引用，或者记进 `notRequirements`。只追到编号的表会漏掉句子——「FR-3 已覆盖」是一句没人核对的话，倍速、水印、快捷键就是这样从表里消失的。

**「别处已经覆盖」不是理由。** 一个功能小节的每句话，要么被某一行引用，要么各自说明它为什么不是需求。

### 证据（evidence）

一条证据是一条可以再跑一遍的命令，退出码 0 表示它量的那几句话成立。「已人工确认」「见截图」「代码里有」都不是证据。每条证据要写四样：

| 字段 | 含义 |
|---|---|
| `run` | 命令 |
| `surface` | 它量的是哪一端（必须是该需求 `surfaces` 里的一个） |
| `level` | 它量到哪一层：`logic`（逻辑/单元）、`interface`（真的经过接口和存储）、`ui`（真的操作界面） |
| `covers` | 它量的是这一行的哪几条条款，**每条各写**这句话不成立时它会怎么失败 |

```json
"covers": [
  { "clause": "FR-3.a", "failsWhen": "倍速菜单里选 2x 后 playbackRate 不是 2" },
  { "clause": "FR-3.b", "failsWhen": "按右方向键后播放位置没有前进 0.5 秒" }
]
```

**每条条款都要有证据量它。** 一条验收里有七件事，就要有证据分别说清这七件事各自怎么让它失败——一条只测了其中一件的证据，只能 `covers` 那一件，其余六件会被脚本报为没人量。

`failsWhen` 是对这条测试**实际断言了什么**的陈述。写之前先读它的断言；它没断言的，不要写。

### 端与层级（surfaces）

每条需求写明它**落在哪些端**，以及每个端**至少要量到哪一层**：

```json
"surfaces": [
  { "name": "backend", "level": "interface" },
  { "name": "web", "level": "ui" },
  { "name": "ipad", "level": "ui" }
]
```

规则：**每个端至少有一条层级够的证据。** 一条「老师在 iPad 上给作业打分」的需求，如果 iPad 这一端只有逻辑层测试，脚本会报错——逻辑层测试证明不了界面接上了。

怎么定层级：需求说的是人看得见、点得到的东西，就是 `ui`；说的是系统对外的行为（接口返回什么、数据怎么存），就是 `interface`；只有纯计算规则才是 `logic`。拿不准时取高的。

### 批次出口不手写

`batches` 里**没有**出口检查字段。一个批次的出口就是：**它名下的全部证据都通过。** 由 `spec-accept` 的脚本直接运行这些证据来判定：

```bash
python3 ~/.agents/skills/spec-accept/scripts/run_evidence.py <计划目录>/trace.json --batch <批次号> --cwd <项目根目录>
```

校验通过后脚本会把每个批次的这条命令打印出来，原样用作议程里该阶段的出口检查。

**项目里不再另设出口脚本。** 已经有一个手写的出口脚本时，不要让它和证据「两者都过才算」——那是两套判据，迟早各走各的。把它拆掉：

- 它里面量某条需求的检查，改写成那条需求的证据。
- 它里面不属于任何需求、但每次出口都该过的检查（没有新增的测试失败、迁移能往返、类型检查通过），写成 `guards`：

```json
"guards": [
  { "id": "G1", "run": "cd backend && uv run pytest -q", "why": "没有弄坏已有的行为", "batches": ["B7"] },
  { "id": "G2", "run": "cd clients/web && npm run typecheck", "why": "类型仍然自洽" }
]
```

`batches` 不写就对每个批次生效。守卫和证据由同一个脚本运行，任何一条不过，批次都不能出口。守卫不能代替证据：它证明没弄坏别的，不证明做成了这件。

为什么不许手写：出口脚本和证据一旦是两处，就会各走各的——计划要界面测试，脚本只跑单元测试。让出口**就是**证据，这个缺口不存在，执行的人也没有一个可以改松的出口脚本。

## 流程：验收先行

顺序不能换。先有证据，再有设计，最后才有任务。

### 第 1 步　把需求拆成可检验的条目

- 每条一个稳定编号（`R1`、`R2`…），之后只追加、不重排。
- 每条必须能回答：**怎样的一次操作、看到什么结果，算它成立？** 答不出的不是需求，是愿望——列出来退回给需求所有者，不要自己补全。
- 一条里有「并且」的，拆成两条。
- **验收条目各占一行。** 需求书里若有验收清单，把它列进 `acceptanceItems`，每一条对应表里**恰好一行**，在那一行写 `"acceptance": "7"`。不要把「验收 7、8、9」并进一行的标题：需求所有者是按条验收的，三条并成一行，其中一条不满足时整行只能笼统地算没过，分不清是哪条。
- **功能小节里的每句话都要落到某一行。** 一条验收条目常常只说了功能小节里的一部分。把小节里和这条验收是同一件事的句子引进这一行；剩下的句子（验收清单没提到的）另起行。不能因为「这个小节有验收条目了」就算它整个覆盖了。
- **需求书里的每个编号都要有交代。** 填 `documents.requirementIdPattern`。一个编号要么是表里的一行，要么它小节下的每句话都被引用了，要么记进 `notRequirements` 并写明 `kind`。
- 逐段对照需求书：每一句带「必须、应、不得、可以」的话，都要被某一行的 `clauses` 引用。列表项和表格行脚本会替你查全；**写在段落正文里的句子脚本查不到**，要自己逐段读，拆完请需求所有者过目。

### 第 2 步　定每条需求的端和层级，写证据——在写任何设计之前

- 先填 `surfaces`，再为每个端写证据。
- 此刻证据应该是**失败**的（功能还不存在）。现在就通过的证据，要么功能已有，要么没量到东西。
- 禁止不可能失败的命令（`true`、`echo ok`）。脚本会拒绝。
- **一条命令只当一条证据。** 证据要指到只量这条需求的那个用例（`pytest path::test_name`、`playwright test -g '用例名'`、`-only-testing:…`），不要指到一个什么都测一点的大用例或整个文件。两条需求的证据是同一条命令，脚本会拒绝。

### 第 3 步　写设计，每一节挂到需求上

- 设计书每个决定标明它服务于哪些需求编号，登记进该需求的 `design`。
- 反查两遍：有没有需求在设计里找不到落点？有没有哪节设计不服务于任何需求（那是范围蔓延，删掉，或者回去请需求所有者加需求）？

### 第 4 步　写计划，任务从需求推出来

- 每个任务标明它为哪些需求而存在；每条需求至少有一个任务。
- **任务的「完成」= 它名下需求的证据通过。** 不用勾选框当完成标准。
- 把每条证据归入一个批次（`batches[].evidence`）。一条证据归在哪个批次，那个批次做完时它就必须通过。

### 第 5 步　跑校验，不过不交

```bash
python3 ~/.agents/skills/spec-trace/scripts/trace_check.py <计划目录>/trace.json
```

有任何一条报错就不算写完。

### 第 6 步　变更时

- 需求变了：先改 `requirements`，再顺着改证据、设计、任务，最后重跑校验。**不要只改计划。**
- 做不完的事：记进 `leftovers`，**必须**写明欠的是哪条需求。它算不算「不阻塞」不由记下它的人决定。
- 推迟一条需求：`status` 改为 `deferred`，并填 `deferral`（谁批准、哪天、为什么）。批准人必须是需求所有者。

## 给已有项目补追溯表

文档和代码都已经在了，要回头补这张表时，最容易犯的错是**拿现有的测试去找需求认领**：项目里有两个浏览器测试，于是十条需求的界面层证据都指向它们，每条再配一句写得很具体的「什么情况下会失败」。表面上每个端都有层级够的证据，实际上那两个测试量没量到这十件事，没有人核对过。

顺序要反过来：

1. **先只看需求。** 对每一行写出证据**应该**量什么——哪一次操作、看到什么结果。这时不要打开测试目录。
2. **再去找现有测试。** 打开用例读它的断言，逐条对：它真的做了那次操作、断言了那个结果吗？
3. **量到了**：证据指到这个具体用例，`covers` 只列它实际断言了的条款，`failsWhen` 写它实际断言的东西，不写你希望它断言的东西。
4. **没量到，或只量到一部分**：写一条**待补**的证据——命令指向一个还不存在的用例，现在跑会失败。这是这张表该有的样子：它如实说出缺了什么。
5. 一个现有用例最多充当一条证据。它顺带覆盖了别的需求，那些需求仍然各要自己的证据。

补完后表里有许多现在会失败的证据是正常的，说明表是诚实的。全部通过反而要怀疑。

## 校验规则

`trace_check.py` 在下列任一情况报错：

| 规则 | 它拦的是什么 |
|---|---|
| 生效的需求没有任务 | 需求写了没人做 |
| 生效的需求没有设计出处 | 设计漏了它 |
| 生效的需求没有写落在哪些端 | 不知道该量哪里 |
| 某个端没有层级够的证据 | 界面需求只有逻辑测试 |
| 证据量的端不在该需求的端里 | 证据量错了地方 |
| 证据没有命令，或命令不可能失败 | 假证据 |
| 一行没有引用需求书里的任何句子，或引文不是原话 | 只追到编号，没追到句子 |
| 需求书小节下有列表项或表格行没被任何一行引用 | 一句要求从表里消失了 |
| 条款没有任何证据量它 | 一条证据只量了七件事里的一件 |
| 证据没按条款写「不成立时怎么失败」 | 证据没想清楚量什么 |
| `notRequirements` 的 `kind` 不是三种之一 | 用「别处已覆盖」放过一条需求 |
| 守卫没有命令、命令不可能失败、没写防什么 | 假守卫 |
| 两条证据用的是同一条命令 | 拿一个测试充当好几条需求的证据 |
| 证据没有归入任何批次 | 没有哪个出口会去跑它 |
| 任务不指向任何需求 | 范围蔓延 |
| 需求与任务互相引用不一致 | 两张表各说各话 |
| 批次名下没有证据 | 空批次 |
| 批次带了手写的出口检查 | 出口和证据脱节的入口 |
| 遗留项没有挂到需求上 | 自己决定「不阻塞」 |
| 推迟的需求没有批准记录 | 自己推迟需求 |
| 编号在对应文档里找不到 | 表和文档漂移 |
| 需求书里的编号不在表里，也没记进 `notRequirements` | 漏了一条需求 |
| 没写 `requirementIdPattern` 或 `documents.plan` | 上面两项查不了 |
| 没写 `acceptanceItems` | 分不清是没有验收条目还是忘了列 |
| 验收条目没有对应的行，或被几行同时认领 | 验收时有一条量不到 / 分不清 |
| 一行的 `acceptance` 是列表 | 几条验收并在一行 |

## 不要做的事

- 不要先写计划再回头补追溯表。那样表只会如实记录计划的漏洞。
- 不要让一条证据同时证明五条需求。一条挂了，分不清是哪条没满足。给同一条命令起五个证据编号是同一件事。
- 不要写你没读过断言的 `failsWhen`。它是对这条测试实际量了什么的陈述，不是愿望。
- 不要只看校验的报错来凑这张表。报错告诉你哪里对不上，不告诉你该怎么对上——那在上面的流程里。规则变了（脚本会打印规则版本）就重新加载这个 skill 再改。
- 不要保留一个和证据并行的出口脚本。
- 不要把「跑全量测试通过」当作任何一条具体需求的证据。它证明的是没弄坏别的，不是做成了这件。
- 不要为了让校验通过而把层级写低。层级是需求决定的，不是测试写起来方便不方便决定的。
