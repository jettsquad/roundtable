# 需求验收（spec-accept）

## 这个 skill 管什么，不管什么

**管：** 交付出来的结果，是否满足需求。依据是文档阶段留下的追溯表 `trace.json`。

**不管：** 需求、设计、计划写得对不对（那是 `spec-trace` 的事）；怎么把没满足的做出来（那是执行的事）。

验收只做一件事：**把证据跑一遍，如实报告。** 不修代码，不改追溯表，不替任何一条需求说情。

## 两种用法

### 判定一个批次能否出口

```bash
python3 ~/.agents/skills/spec-accept/scripts/run_evidence.py <计划目录>/trace.json --batch <批次号> --cwd <项目根目录>
```

运行该批次名下的全部证据，以及追溯表里对这个批次生效的守卫（`guards`：不属于任何需求、但出口都要过的检查）。全部通过，退出码 0；否则非 0，并列出哪条没过。议程里每个阶段的出口检查就是这条命令——项目里没有、也不应该有另一个出口脚本。

### 全量验收

```bash
python3 ~/.agents/skills/spec-accept/scripts/run_evidence.py <计划目录>/trace.json --cwd <项目根目录>
```

运行全部证据，按需求给出结论，写入 `acceptance.json`：

- **满足**：该需求的证据全部退出码 0，且没有遗留项挂在它上面。
- **未满足**：任一证据失败、超时，或有遗留项。
- **已推迟**：有需求所有者的推迟记录。单列，不算满足。

守卫也会全部运行一遍，结果单列。有任何未满足，或任何守卫没通过，退出码非 0。

## 纪律

1. **以跑出来的为准。** 不采信任何人说的「已完成」，包括你自己。
2. **不修。** 发现没满足就记为未满足，交回去做。顺手修一下，等于验收的人参与了被验收的东西。
3. **不改证据。** 证据是文档阶段定的。你认为某条证据没量到需求——它通过了，功能其实不对——**不要自己加一条再判**，按下一节处理。
4. **「大部分做了」是未满足。**
5. 未满足的每一条，报告里写清：缺什么、证据输出的最后几行。这份清单是下一轮工作的输入。

## 发现证据本身不对时

验收中可能遇到：证据通过了，但你有具体理由认为需求没满足（例如证据测的是逻辑层，而界面根本没接）。

这**不是验收阶段能解决的问题**，是文档阶段的缺陷：追溯表里这条需求的证据没量到它。处理方式：

- 在报告里把它单列为「证据不足」，写明哪条需求、哪条证据、为什么量不到。
- 这一条退回文档阶段，由那里改追溯表（必要时改 `spec-trace` 的规则），再重新验收。
- 不要在验收里把它悄悄记成未满足然后继续——那样下一次同样的漏洞还会出现。

## 输出

`acceptance.json` 的结构：

```json
{
  "at": "2026-10-11T20:00:00",
  "met": 12, "unmet": 3, "deferred": 1,
  "requirements": [
    { "id": "R1", "title": "…", "verdict": "unmet",
      "reasons": ["证据 E2 未通过", "遗留项 L1：…"],
      "evidence": [{ "id": "E2", "run": "…", "exitCode": 1, "tail": "…", "seconds": 4.2 }] }
  ]
}
```
