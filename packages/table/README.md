# @squad/table — `ctx.teams`

桌子：主持人通过它行动的那个插件。四个插件里的 ①。

## 拥有

- 团队生命周期：建团、席位名册、销毁
- **主持人节点**：创建并持有它（`ctx.agents.create()`，cwd = 团队项目文件夹）
- 轮次编排：谁先说、等谁、独立还是累积
- 席位翻译层：把席位配置翻成 `SubagentStartRequest`，把回复翻回团队记录
- 团队记录：`session.append()` 到主持人节点的日志

## 绝不拥有

| 不拥有 | 归谁 |
|---|---|
| 「每个席位看见什么」的决策 | ② `ctx.teamContext` |
| 任何文本判断（检查点、议程、交接） | ③ `ctx.secretary` |
| 判据库与它的召回 | ④ `ctx.reasoning` |
| 席位的执行细节（起进程、认证） | DSH 的 subagent provider |

## 两条硬不变量

**主持人节点是锚点，不是决策者。**DSH 要求每个 subagent 有一个 parent Agent 提供
cwd、血缘与授权，它只做这件事。派谁发言、什么顺序，全部由这里的确定性代码执行。
**它的模型一旦参与决定，就是让 LLM 当主持人**——那是这个产品唯一不能是的东西。

实现上的体现：团队记录一律 `session.append()`，**绝不用 `followup()`**
（会唤醒它跑一个 LLM 回合）**也不用 `inject()`**（消息停在 inbox 不进日志，
团队一安静记录就丢尾巴）。两种都试过，两种都错。

**席位之间没有直接通道。**甲看见乙说了什么，只因为桌子把它放进了甲的 prompt。
所以「独立作答」是拓扑事实，不是系统提示词里的一句承诺。
