# @squad/secretary — `ctx.secretary`

秘书：**唯一被允许替主持人做判断工作**的席位。四个插件里的 ③。

## 拥有

- 上下文检查点的提示词、生成与校验（`checkpoint.ts`）
- 议程中止交接文档的提示词、生成与校验（`termination.ts`）
- 「产出算不算数」的判定：不完整一律拒收（`tasks.ts`）
- 议程草案（`draftAgenda`）—— **未建**，与桌子的议程状态机一起做

## 绝不拥有

| 不拥有 | 归谁 |
|---|---|
| 检查点**存在哪**、**什么时候进窗口** | ② `ctx.teamContext` |
| 什么时候**该**写检查点（阈值） | ② `ctx.teamContext` |
| 议程状态机、谁发言 | ① `ctx.teams` |
| 判据库 | ④ `ctx.reasoning` |
| 任何团队状态 | 没有人——见下 |

## 无状态是构造出来的，不是约定

每次调用开一个全新的 one-shot 子 agent，用完扔掉；任务需要的一切由**调用方投喂**——
接续检查点是把上一份**放进提示词**，而不是放在这里的某个字段里。

于是没有东西会累积，也就没有东西会在两次调用之间漂移；两个调用方不可能看到不同的秘书。

它**没有自己的 agent**。dsh 要求每个 subagent 有一个 parent 提供 cwd、血缘与授权，
所以调用方传团队的主持人节点进来。秘书因此是**主持人执行的一项任务**，不是有独立身份的团队成员。

## 为什么这里的失败一律是拒收

这两份文档是**下游当作事实读的东西**：检查点会变成后续每一轮的历史，交接文档会变成
下一支团队的起点。而**缺一节不会自报家门**——它读起来就是「这方面没有内容」。

- 检查点少了「未决分歧」，读起来不像坏了，读起来像**这支团队达成了共识**，
  之后每一轮都继承一个从未发生过的一致意见。
- 交接文档少一节，接手的人会当成那一节本来就是空的，从错的地方开始。

所以：四个/五个标题缺一个就抛错，并**点名缺了哪一个**。

`stopReason` 不是 `completed` 也一律拒收。最危险的是 `max-tokens`——它返回的是**真文本，
只是中途停了**，能通过标题校验，然后以半句话结尾。
