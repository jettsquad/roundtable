# @squad/reasoning — Lil X（`ctx.reasoning`）

使用者自己的**判断标准库**。四个插件里的 ④。

## 拥有

- 判据（抽象）与实例（原始情境）的存放格式与目录
- 处境三轴：框架位置 / 动作类型（闭合 7）/ 特征标记（闭合 8）
- 捕获：把「人推翻了机器」这件事记成实例
- 提炼：起草一条**待裁定**的提议（关系判定 + 抽象表述）
- 裁定：人 accept / reject / 改写后接受

## 绝不拥有

| 不拥有 | 归谁 |
|---|---|
| 任何团队状态 | ① `ctx.teams` —— **`inject` 里刻意没有 `teams`** |
| 检查点、议程的文本判断 | ③ `ctx.secretary` |
| 「席位这轮看见什么」 | ② `ctx.teamContext` |

**它是用户级的，不是团队级的。**一个只能从项目内部写入的库，正好是「可以带走的资产」的反面。

## 三条不可动摇的

**只捕获程序零误判的信号。**当前只有一种：人否决了机器的提议。**明确不做**从对话里自动挖掘——
噪声大，而且会大量捕到**结论**（「他选了 Postgres」）而不是**标准**（「他要求给出迁移成本估算
才接受选型」）。这个区分是整件事的生死线。

**人裁定不能省。**这里没有任何东西会自己生效。系统在修改自己的评分标准，自动通过等于让它
自己给自己打分。一切落在 `proposals/`，等人。

**实例先写，再去问模型。**发生过的事是事实，提炼是对它的看法。模型调用失败时事实必须已经在盘上——
反过来写，丢掉的正好是系统最没把握的那些случае，而那些才是值钱的。

## 反例为什么是四种关系里最重要的一种

反例是系统能收到的**最大梯度**。它意味着两件事之一：判据错了（推翻），或判据的适用边界比
原来写的窄（收窄）。**第二种更常见，也更有价值。**

「不可见 = 不可纠正」这条的边界——*动作平凡可逆时不适用（没人要求每次自动格式化都弹窗）*——
**只可能从反例里学到**。没有反例通道，抽象会随着每次确认变得更绝对，最后变成一句没有适用
条件的口号。

## 存放：结构负责被找到，散文负责被读懂

```
<root>/
  criteria/    抽象 —— 可迁移、可以给别人
  instances/   实例 —— 本人的、带项目细节、不出门
  proposals/   待人裁定
```

两个极端都不行：纯散文没法判断「要不要捞它」（每次都要模型读全部）；纯结构化把「为什么」
压扁了，而「为什么」是判据里唯一值钱的部分。所以 front matter 放触发条件，正文放主张与边界。

**这个模式已在小尺度上验证过**：检查点的四个固定标题是结构，正文是判断。同一思路放大。

## 导出边界就是目录切分

> **抽象可导出，实例不可。**

这不需要额外设计，也不需要任何隐私标记：它是「文件在哪个目录」这个事实，不是某个未来的导出
程序需要记住的规则。同一个决定同时解决了「出厂初级版」和「隐私」两件事。

## 为什么现在没有相似度计算

主键是**处境**，不是文本。「不可见 = 不可纠正」学自检查点折叠，**该触发于自动重试、自动降级**
——文字上八竿子打不着，处境上完全同构。按文字找永远找不回来。

而这恰恰是最值钱的一次召回：同话题的召回人自己也想得起来，**跨话题的只有系统能提醒**。

以单用户规模，触发条件粗过滤之后把候选全给模型读，比任何相似度算法都准——因为**模型读得懂
「适用边界」，算法读不懂**。先做对，再做快；过早上这层会把「触发条件怎么设计」这个真正的
难题掩盖掉。
