# @squad/migrate — 一次性的 1.x → 2.0 搬迁

阶段 4。**手工挂载、跑一次、不进任何出厂组合。**

## 它为什么存在

1.x 里唯一不能重建的东西是**已经发生过的讨论**。切换不该意味着放弃它们。

## 一条规矩决定了其余一切

> **有任何一处读不懂，这支团队就不迁。**

部分迁移会产出一支**看起来迁好了、中间有个洞**的团队——而没人会发现那个洞，因为
「丢掉的那个东西存在过」的唯一证据，正是丢掉的那个东西。

拒绝的代价是一个人十分钟；静默的缺口，代价是他从此以为自己的历史是完整的。

实测（构造的坏数据）：

```
[t-bad] 有问题的团队：⚠️ 有 2 处读不懂，**不迁移这支团队**：
    - 第 2 条事件的类型「someKindFrom1x」不认识
    - 第 3 条发言来自名册上没有的席位「ghost」
```

同一次运行里，另一支干净的团队照常迁移——**拒绝是按团队的，不是按整批的**。

## 默认试运行

`dryRun` 默认为真：报告会迁什么、读不懂什么，一个字节都不写。要真迁必须**显式**设成 false。

## 迁完会回读

不靠「没抛错」当成功。迁完之后把窗口读回来，检查检查点在不在、产出对不对得上，对不上就报警——
这个项目在别处都不做的那种声明，这里也不做。

## 两处保真的细节

**turnId 原样保留。**迁移过来的检查点，它的 `coversUpTo` 指的是 1.x 的 turn id。这里重新生成 id
的话，每一份带过来的检查点都会覆盖到一个不存在的边界，装配层会把它们读成「覆盖范围不在日志里」。

**作废状态跟着走。**主持人当年否决过的检查点，不能因为迁移而复活——那比不迁它更糟：
团队会带着一个它主人已经推翻过的历史截断点回来。

## 事件类型没有 catch-all

每个 1.x 事件类型要么被处理，要么显式列进「不携带任何内容」，要么被报告。和渲染层三张表同一个道理。
